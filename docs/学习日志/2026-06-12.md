## Groundedness 与 Faithfulness

```text
Groundedness
    检查答案和证据是否包含预定义关键事实

Faithfulness
    检查答案是否改变、夸大或反转证据语义
```

测试案例中，两个回答都包含“流式识别”：

```text
当前系统尚未实现流式识别
→ Faithfulness 通过

当前系统已经完整实现流式识别
→ Faithfulness 失败
```

Judge 能识别“未来改进方向”和“已经实现”之间的语义矛盾，这是关键词匹配无法完成的。

## 核心工程概念

### 依赖注入

生产环境默认调用 DeepSeek，单元测试传入 `fake_llm`。这样测试不消耗 API，速度快且结果稳定。

### 指标分层

```text
路由正确
→ 参数正确
→ 任务完成
→ 关键事实有证据
→ 回答语义忠实
```

LLM-as-Judge 不是绝对真理。它也可能受到提示词、模型随机性和上下文长度影响，因此后续还需要 Judge benchmark、重复运行稳定性和人工复核。

### 指标含义

```text

    每个案例中占多数预测的比例，再对全部案例取平均

unanimous_rate
    所有重复运行都给出相同结果的案例比例

majority_accuracy
    多数投票结果与人工标签一致的案例比例
```

例如三次预测为：

```text
[True, False, True]
```

则：

```text
majority_prediction = True
agreement_score = 2 / 3
unanimous = False
```

## 评估报告回归对比

### 新增模块

```text
app/evaluation_report_comparator.py
```

主要函数：

```text
load_evaluation_report()
compare_evaluation_report_files()
compare_evaluation_reports()
```

### 为什么按案例名称对齐

不能直接比较：

```python
baseline["results"][0]
current["results"][0]
```

因为 benchmark 的案例顺序可能变化。

当前实现先把结果转换为：

```python
{
    "案例名称": case_result
}
```

再根据共同的 `name` 对齐。这样调整 JSON 列表顺序不会产生假回归。

### 检测的变化

Faithfulness：

```text
accuracy 下降
actual_passed 翻转
正确预测变为错误预测
```

稳定性：

```text
average_agreement 下降
unanimous_rate 下降
majority_accuracy 下降
单案例 agreement_score 下降
单案例从 unanimous=True 变为 False
多数投票结果翻转
```

通用变化：

```text
Judge 模型变化
评估配置变化
新增 benchmark 案例
删除 benchmark 案例
```

### 一个重要边界

Faithfulness Judge 的原始 `score` 下降不一定代表质量退化。

例如负例的人工标签是“不忠实”：

```text
score 从 1.0 降到 0.0
```

反而可能说明 Judge 从错误变为正确。

因此：

- 原始 score 变化会记录
- score 下降不会直接计入 regression
- 是否退化以 `prediction_correct` 为主要依据

这是指标设计中的基本原则：必须先理解指标语义，不能机械地认为数值越大越好。

## 回归容忍阈值

新增两个 CLI 参数：

```text
--metric-tolerance
--stability-tolerance
```

含义：

- `metric_tolerance`：允许总体指标下降的最大值
- `stability_tolerance`：允许单案例一致率下降的最大值

例如：

```powershell
python -m app.cli compare-evaluation-reports `
  --baseline baseline.json `
  --current current.json `
  --metric-tolerance 0.02 `
  --stability-tolerance 0.05 `
  --fail-on-regression
```

如果 accuracy 从 `1.0` 降到 `0.99`：

```text
drop = 0.01
tolerance = 0.02
不算回归
```

如果 accuracy 降到 `0.95`：

```text
drop = 0.05
tolerance = 0.02
判定回归
```

预测从正确变为错误不受阈值保护，因为这属于明确的案例级质量退化。

### 浮点数边界

测试中发现：

```python
1.0 - 0.98
```

在计算机中可能得到：

```text
0.020000000000000018
```

它会让“下降恰好等于阈值”的情况被误判。因此比较时加入：

```text
FLOAT_COMPARISON_EPSILON = 1e-12
```

这是因为浮点数使用有限二进制位近似表示十进制小数，不能假设所有小数运算都精确相等。

## GitHub Actions 离线 CI

### 新增 Workflow

```text
.github/workflows/ci.yml
```

触发条件：

```text
push
pull_request
workflow_dispatch
```

含义：

- `push`：推送代码后自动运行
- `pull_request`：创建或更新 PR 时运行
- `workflow_dispatch`：允许在 GitHub 页面手动运行

### GitHub Actions 的层级

```text
Workflow
  └─ Job
      └─ Step
```

本项目中：

```text
Workflow: CI
Job: offline-quality-gate
Steps:
  1. Checkout repository
  2. Install uv and Python
  3. Install locked dependencies
  4. Prepare report directory
  5. Run offline tests
  6. Run offline regression quality gate
  7. Upload CI reports
```

`Runner` 是执行 Job 的机器。当前使用：

```yaml
runs-on: ubuntu-latest
```

也就是 GitHub 临时提供的一台 Linux 虚拟机。

### 为什么使用 frozen

```powershell
uv sync --frozen --all-groups
uv run --frozen pytest
```

`--frozen` 要求严格使用现有 `uv.lock`，不在 CI 中自动修改依赖解析结果。这样本地和 CI 更容易保持一致。

### 为什么 CI 使用假的 API Key

当前 `app/config.py` 在导入时要求存在：

```text
DEEPSEEK_API_KEY
```

但离线测试中的 LLM 都使用 fake function，不会发送真实网络请求。因此 workflow 设置：

```yaml
env:
  DEEPSEEK_API_KEY: offline-ci-placeholder
```

它只负责通过配置校验，不具备真实 API 权限。

默认 Pull Request CI 不应使用真实 API Key，原因包括：

- 避免恶意 PR 读取密钥
- 避免每次提交产生调用费用
- 避免网络波动导致离线测试不稳定

### 离线回归门禁

新增固定夹具：

```text
tests/fixtures/evaluation_reports/
```

CI 使用 baseline 和 current 静态报告验证：

- 报告读取
- 指标比较
- CLI 退出码
- JSON 报告保存
- Markdown 摘要保存

这属于对“评估基础设施”的离线测试，不代表重新执行了一次真实 LLM Judge。

### Artifact

CI 会上传：

```text
data/reports/pytest.xml
data/reports/offline_regression.json
data/reports/offline_regression.md
```

Artifact 是一次 Workflow 运行产生的可下载文件。本项目保留：

```text
14 天
```

并使用：

```yaml
if: always()
```

因此即使测试失败，只要报告已经生成，上传步骤仍会尝试保存现场。

### 并发与权限

```yaml
permissions:
  contents: read
```

CI 只需要读取仓库，不需要写入代码。

```yaml
concurrency:
  cancel-in-progress: true
```

同一分支连续推送时，旧运行会被取消，减少重复计算。

## 手动在线评估 Workflow

新增：

```text
.github/workflows/online-evaluation.yml
```

它与离线 CI 的区别：

| Workflow | 触发方式 | 真实密钥 | API 费用 |
| --- | --- | --- | --- |
| CI | Push / PR / 手动 | 不使用 | 无 |
| Online Evaluation | 仅手动 | 使用 Secret | 有 |

### 为什么仅允许手动触发

在线 Judge 会产生网络请求和费用。如果每次 Push 或 PR 都运行：

- 开发过程中会重复扣费
- 网络波动可能导致正常 PR 失败
- 外部贡献者可能间接触发密钥使用
- 很难控制稳定性重复次数

因此使用：

```yaml
"on":
  workflow_dispatch:
```

只有具备仓库写权限的人才能从 Actions 页面主动运行。

### Workflow 输入

运行时可以选择：

```text
run_stability
repeat_count
min_accuracy
min_average_agreement
min_unanimous_rate
min_majority_accuracy
```

重复次数使用 `choice`，只开放：

```text
2
3
```

这样不能误填非常大的数字，形成基本的费用上限。

当前 benchmark 有 4 个案例，因此预计调用次数：

```text
只运行 Faithfulness：
4 次

Faithfulness + 2 轮稳定性：
4 + 4 × 2 = 12 次

Faithfulness + 3 轮稳定性：
4 + 4 × 3 = 16 次
```

### GitHub Secret

代码中只写：

```yaml
DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}
```

真实值需要在 GitHub 页面配置：

```text
仓库 Settings
→ Secrets and variables
→ Actions
→ New repository secret
→ Name: DEEPSEEK_API_KEY
→ Secret: 真实 DeepSeek API Key
```

Secret 与普通环境变量的区别：

- Secret 的值不会写入仓库
- GitHub 会尝试在日志中隐藏 Secret
- Workflow 必须显式引用后才能读取
- Pull Request 默认离线 CI 不引用该 Secret

不要把真实 Key 写入：

```text
workflow YAML
.env.example
README
测试夹具
日志与 Artifact
```

### 失败现场保存

Faithfulness 和稳定性步骤都使用：

```yaml
continue-on-error: true
```

这不是忽略质量问题，而是先让后续步骤有机会：

- 继续收集另一份评估报告
- 上传已经生成的 Artifact
- 保存失败原因

最后由 `Enforce online quality gate` 统一检查两个步骤的 outcome，并在有失败时返回退出码 1。

流程是：

```text
运行评估
→ 保存报告
→ 上传 Artifact
→ 最终门禁决定 PASS / FAIL
```

### 调用安全边界

- Workflow 仅手动触发
- 仓库权限为 `contents: read`
- 重复次数限制为 2 或 3
- Job 最长运行 15 分钟
- 缺少 Secret 时立即失败
- 同一分支不会自动取消正在进行的在线评估

### 重要限制

GitHub 要求带 `workflow_dispatch` 的 Workflow 文件先存在于默认分支，Actions 页面才会显示 `Run workflow` 按钮。
